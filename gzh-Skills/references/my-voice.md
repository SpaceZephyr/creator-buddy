# 个人文风档案

作者：**空格的键盘**（公众号 / 小红书 / B站 / 知乎）

被 `gzh-longform-writer` 和 `gzh-short-post` 共享。作者说「用我的风格」时读取本文件，把下面的规则当**硬约束**执行。

> **样本说明**：本档案提炼自 3 篇全文（《飞书 CLI 已破万星 Star，Agent 接管 SaaS 时代已开》《腾讯 QClaw 实测：当小龙虾爬进 14 亿人的微信》《从"氛围编程"到"氛围工作"：Claude 4.6 揭示的残酷真相》）+ 59 篇标题的主题分布。样本偏小，遇到与实际写作明显冲突的规则，以作者当下判断为准，并回来更新本文件。

---

## 一、开头：时间锚点 + 个人动作

**开头第一句必须包含一个具体时间和一个具体动作。** 三篇无一例外。

- "前两天打开 GitHub，看到飞书官方开源的 lark-cli 仓库星标过万了。"
- "昨晚刷朋友圈的时候，看到一条消息愣了一下——腾讯正在内测一款叫 QClaw 的产品。"
- "昨天深夜，Anthropic 发布了 Claude Opus 4.6。"

**禁止**："最近""如今""随着 AI 的发展""大家可能都注意到了"。

开头之后常跟一句情绪或态度的表态，再进入正题：

> "说实话，我已经有点麻木了。每个月都有新模型，每个都说自己是革命。但这次不一样。"

---

## 二、段落：极短，常一句一段

这是最鲜明的特征。**默认一到两句一段，单句成段是常态。**

关键的判断句**必须单独成段**，前后留白：

> 从 0 到 10,000，用了 45 天。
>
> 平均每天有 219 个 GitHub 开发者点了那颗星。

**禁止**：连续 4 行以上的段落。写出来就拆。

---

## 三、自问自答是核心节奏工具

作者高频使用，**不要因为它在通用 AI 腔黑名单里就删掉**。

规则：问句独立成段，答句**必须具体**。

> 这意味着什么？
>
> 以前你用 AI 写代码，是 1 对 1 的对话。你描述需求，它生成代码，你检查修改。
>
> 现在，你给 Claude 一个需求，它自己分析、自己规划、自己分配任务。

常用问句：`这意味着什么？` / `它能做什么？` / `为什么这事值得关注？` / `你做了什么？`

**判断标准不变**：答句写完，把问答一起删掉——如果没损失信息，那就是 AI 腔，删。

---

## 四、小节标题：编号 + 短

两种都用，一篇里只用一种：

- `一、` `二、` `三、` `四、` `五、写在最后`
- `1、` `2、` `3、`

标题要短、要有信息，不要用"其一""其二"。参考真实标题：

> `1、Agent 是怎么访问 SaaS` / `2、飞书的底牌不是 CLI 本身` / `二、"氛围编程"的死亡宣告` / `三、为什么很多人会掉队`

**"最后" / "写在最后"是固定的收束节。** 长文必有。

---

## 五、具体数字前置

有数字就往前放，且要能被验证。

> "从 0 到 10,000，用了 45 天。平均每天有 219 个 GitHub 开发者点了那颗星。"
> "Claude 3 到 Claude 4 用了多久？一年。Claude 4 到 Claude 4.6 用了多久？半年。"

**禁止**：没有来源的伪精确数字。

---

## 六、对比框架

作者习惯用两组对照来搭骨架，至少用一组：

- **国内 vs 国外**（飞书 vs Notion/Slack/Linear）
- **以前 vs 现在**（1 对 1 对话 vs Agent Teams）
- **工具 vs 承包商 / 工匠 vs 甲方**（身份转换）
- **表面 vs 底牌**（"飞书的底牌不是 CLI 本身"）

---

## 七、口语标记

自然出现，不要刻意堆：

`说实话` / `我觉得` / `其实` / `挺有意思的` / `这才是真正的` / `给大家提供一些我的玩法` / `对吧？`

**第一人称密度高。** 每个大段落至少一处"我"的判断。

---

## 八、实操类内容用「玩法」编号

写工具、教程时的固定结构：

```
给大家提供一些我的玩法

玩法一：基础玩法
……

玩法二：本地文章推到飞书云文档
……

玩法三：飞书文档当我的网站 CMS
……
```

每个玩法都要落到**作者自己真实在用的场景**（Obsidian 写作、播客网站、飞书云文档），不要写通用示例。

---

## 九、结尾

两种，二选一：

**A. 拉高到一个趋势判断**（技术/行业类）

> "飞书引领了 B 端领域的 CLI 化，可以预见，未来会有越来越多的软件开放 CLI 版本给 Agent 使用，对于我们，只需要和 Agent 对话，就能操作 APP。"

**B. 抛回给读者**（观点/争议类）

> "你对 QClaw 怎么看？欢迎在评论区聊聊。"
> "时间窗口还在，但正在快速关闭。你准备好了吗？"

结尾可以带 hashtag：`#飞书 #飞书CLI`

## 十、篇幅

| 类型 | 字数 |
|---|---|
| 长文 | **1300–2100 字**（三篇实际为 1324 / 1998 / 2035） |
| 短文 | ≤1000 字 |

**超过 2200 字要警惕。** 作者的实际节奏偏紧凑，长了会失真。

## 十一、主题边界

59 篇的实际分布：

| 主题 | 占比 |
|---|---|
| Skill / Agent 工程实践 | 约 50% |
| AI 视频 / 影音创作 | 约 8% |
| 云计算 / K8s / 多云 | 约 7%（早期支线，与主线已脱节） |
| 模型与产品实测 | 约 5% |
| 行业趋势观点 | 约 5% |

**主线是 Agent / Skill 工程。** 写这条线时可以默认读者有基础，不必科普；写其他线时要补背景。

---

## 十二、绝对禁止

- 书面腔：`笔者认为` `综上所述` `值得注意的是` `不难看出`
- 鸡汤腔：`希望对大家有帮助` `共勉` `一起加油` `愿你我都能`
- 三段排比收尾
- 长段落（超过 4 行）
- 开头预热（`最近` `随着` `众所周知`）
- 编造的抽象案例（`某互联网大厂` `某位朋友`）—— 作者的例子全部是具体可查的
